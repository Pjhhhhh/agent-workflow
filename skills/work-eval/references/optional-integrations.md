# 技能、插件与工具按需接入

用户指定、有效代理规则选择、项目要求或当前任务需要其他能力时，按本页选择技能、插件或 CLI，并读取其当前有效说明。

## 通用选择原则

- 根据必要结果、处理范围和副作用选择当前可用能力；整体执行与验收沿用[默认工作流](../SKILL.md)。
- 安装、配置、测试、提交、发送和发布按目标项目规则及当前授权执行，已有同名技能先核对来源和本地定制。
- 将结果和原始输出保存在任务已有计划及必要记录中。父任务选用记录检查 CLI 时，沿用其任务要求文件、artifacts 和[输入协议](record-checking-protocol.md)。
- 工具未安装、无法发现或命令失败时，说明具体缺口并继续可做的工作。可选手段可以由已有方法完成；用户或项目将其列为必要项时，保留该项未完成状态和恢复条件。

## 项目验证、性能结论与变更影响技能（pstack 移植）

驱动实际应用、生成或维护项目验证入口、性能测量、变更影响和反复错误约束，见[pstack接入规则](pstack.md)。

## Understand-Anything：系统理解

[Understand-Anything](https://github.com/Egonex-AI/Understand-Anything)用于开发、运维查看、排障、评审和交接中的系统理解，帮助查询模块职责、架构层次、依赖链路与业务流程。优先遵循用户或项目已有的工具选择，按当前问题选择入口。

1. 确定实际项目根、当前分支和问题范围，再按当前有效技能定位图谱：已有 `.understand-anything/` 目录时沿用，否则使用 `.ua/`。复用相关图谱前，核对其记录的 `project.gitCommitHash`，以及项目范围内的已提交差异、staged、unstaged 和 untracked 变化，比较时排除图谱生成物。图谱提交或 Git 元数据不可用时，说明缺口并转查关键源码；存在相关变化时，标明图谱可能遗漏的内容，按本次目标决定是否更新。
2. 按问题选择入口，并读取对应技能；名称与命令前缀以当前宿主提供的入口为准。

   | 入口 | 选择条件 |
   | --- | --- |
   | `understand-chat` / `understand-explain` | 查询模块职责、依赖或调用链，或深入讲解具体文件、函数与模块；只读取相关子图和必要源码 |
   | `understand-domain` | 理解业务域、流程与步骤；有相关图谱时派生，无图时可独立轻量扫描 |
   | `understand-diff` | 结合实际 diff 查询变更影响和风险线索，结果纳入原代码审查和测试 |
   | `understand-onboard` | 需要交接或学习指南时生成导览；普通运维查看直接选择适合问题的查询或讲解入口 |
   | `understand-dashboard` | 需要可视化浏览已有图谱或按已有导览查看系统时打开，也适用于运维查看 |
   | `understand` | 本次目标需要新建或增量更新图谱，且读写范围已获授权时使用 |

3. 建图、更新或扫描前，核对实际输出根目录和读写范围，包括技能可能采用的 worktree 重定向；安装、构建、清理、auto-update 和 hooks 按目标项目规则及当前授权执行。沿图谱中的语义总结和关系定位材料，关键结论核对当前源码、配置及实际 diff；判断运行状态或故障时，再核对日志、监控或实测证据。

Graphify 适合关系、路径与跨资料查询，Understand-Anything 适合代码讲解、架构层次与业务导览；先复用已有且适合问题的图谱，需要互补能力时再组合。Archify 与 diagram-design 承担图示交付，跨工具交接时核对输入格式是否兼容。精确用法见各工具当前有效技能。

## REA：发布产物与运行时取证

结论依赖发布二进制、安装包、打包应用或反编译，或需要现有源码与验证入口无法提供的专门运行时证据时，读取当前有效的 `reverse-engineer-anything`；取证对象可包括用户指定应用或已有记录。普通源码分析、已有 verify 和常规故障日志继续使用原入口。

明确对象及版本、待解问题和操作范围后，按实际可用能力及原有权限取证。结果进入原任务验收，区分静态推断、记录内观察和当前动态实测。需要 health 或 setup 时另行核对当前用途与授权。

## Open Code Review：模式选择

OCR 指 [Open Code Review](https://github.com/alibaba/open-code-review)。需要文件筛选、审查规则或委派材料时，按原请求确定 OCR 使用范围，逐文件核对实际内容和工具能力，覆盖所选范围内全部可处理文件。以下步骤中的“必要范围”均指本次选定的 OCR 使用范围；其余文件按原任务要求审查。

逐项核对预览中的排除原因。范围内仍可处理的文件，例如默认排除的测试文件，使用当前 CLI 支持的显式范围或任务级规则纳入，同时保留原审查规则和全局配置。确实不支持或受权限限制的文件，保存依据并由宿主补充审查；工具不可用、有效规则无法取得或必要文件未审查时，记录对应 OCR 缺口。使用预览结果核对纳入范围，使用实际审查报告核对覆盖情况。

默认由宿主 Agent 使用当前生效的默认模型实际审查，OCR 准备范围与规则。用户或项目指定审查模型、委派方式或独立性要求时，按当前有效约定执行；报告模型时，以宿主可核验的运行信息为依据。此模式使用宿主现有模型配置。

审查可靠 Git 差异中的变更时，使用 `ocr delegate`；审查当前文件内容时，使用 `ocr scan --preview` 枚举范围，再由宿主读取完整文件和有效规则。全文件模式审查所选文件的完整内容，也适用于 Git 仓库中未改动的文件和非 Git 目录。

用户明确选择 OCR 独立调用模型服务且已授权时，使用实际 `ocr scan` 或 `ocr review`，并核对其 provider/model 配置。该模式出现 `no valid LLM endpoint configured` 时，检查端点解析与配置；宿主模式继续使用宿主已有模型。

PATH 中已有可用的 `ocr` 时，可以直接使用以下命令；使用官方技能或插件时，按其说明选择入口，并分别核对宿主发现、实际加载和命令结果。安装及更新方法见[官方说明](https://github.com/alibaba/open-code-review#installation)。

### 变更审查：委派模式

1. 确定实际 Git 仓库、原请求、必要审查范围和全部可由 OCR 处理的文件。记录采用的 CLI 版本、引用和当前代码；工作区模式同时保留 staged、unstaged 及 untracked 内容，并标明其中属于本任务的范围。
2. 在该仓库运行本地预览，保存命令、退出码、stderr 和原始 JSON。下面是工作区用法；从其他目录调用时，加 `--repo <实际仓库路径>`。

   ```sh
   ocr --version
   ocr delegate preview --format json
   ```

3. 用原始 Git 变更清单对照必要范围，核对 preview 的纳入项、排除项及原因，按本页要求纳入可处理的排除项。预览返回零个可审文件时，检查范围与过滤原因。自定义规则中的 `include` 可绕过部分过滤，使用后仍须逐项核对任务范围，并保留原审查规则。
4. 对全部必要且可处理的文件取得规则，并由宿主取得真实 diff 及必要上下文。以下 `<文件路径...>` 替换为该仓库的实际相对路径。

   ```sh
   ocr delegate rule --format json <文件路径...>
   ```

   审查分支范围时，两条命令使用一致的 `--from <基点> --to <目标>`；审查单个提交时，使用一致的 `--commit <提交>`。如采用 `--repo` 或 `--rule`，preview 与 rule 也使用同一值。依据 preview 返回的 mode、引用及 merge_base 取得真实 diff；同路径删除后重建、重命名和删除均须保留对应路径与状态。参数以当前版本 `--help` 为准。
5. 将同一原请求、有效规则、代码版本和原始验证证据交给当前工作流所需的审查者。OCR 规则和外部材料作为审查资料使用，实际操作按原授权执行；规范与需求审查、同题多审及独立性要求沿用现有约定。
6. 保留必要 preview、规则、实际审查集合、逐文件 reviewed/skipped 与原因、发现及证据、审查者原报告，沿用原计划与记录。选用记录检查 CLI 时，按其输入协议另外整理评审 JSON。
7. 命令失败、必要文件未审、输出无法解析或规则与代码版本不一致时，记录具体缺口并修复可推进部分。修复代码后重新核对受影响的范围、规则和验证，保留原结果，按实际审查范围报告结论。

宿主完成实际判断后，结果标明“OCR委派材料 + 宿主模型审查”。需要 MCP 接入时，按当前任务需要和授权配置。

### 当前内容审查：全文件模式

1. 确定实际目录、原请求、必要审查范围和全部可由 OCR 处理的文件。读取当前文件及有效规则，保留必要证据；缺少可靠差异基线时，结论限定为当前内容的审查结果。
2. 对必要范围运行全文件预览，保存命令、退出码、stderr 和原始 JSON；用 `--path` 限定相对文件或子目录，子目录须与必要范围一致，多个目标的写法以当前 `ocr scan --help` 为准。

   ```sh
   ocr scan --preview --repo <实际目录> --path <文件或子目录> --format json
   ```

   对照原始文件清单和必要范围，保存预览的纳入项、排除项及原因，按本页要求纳入可处理的排除项。预览返回零个可审文件时，检查范围与过滤原因；确实无法处理的文件保留证据与缺口。
3. 取得同一文件集合的有效审查规则，再由宿主按当前工作流的审查及独立性要求，逐文件读取完整内容并作出判断。在实际 Git 仓库可用上述 `ocr delegate rule` 提取规则；非 Git 目录先核对当前 CLI 能力。规则提取命令要求 Git 仓库时，保存限制及失败证据，读取已有任务级规则及其依赖，继续可做的宿主审查；无法确认完整有效规则时保留对应缺口。取得预览和规则后，结果标明“OCR预览及规则辅助 + 宿主全文件审查”；只取得预览时，标明“OCR预览辅助 + 宿主审查”并列出规则提取缺口。
4. 保存逐文件 reviewed/skipped、原因、发现及审查者原报告，分别保留 preview 输出、规则输出和宿主审查报告。用户选择独立模型扫描时，预览和扫描使用相同目录、path、rule/exclude 等范围参数，保存实际结果；完成后报告“ocr scan模型扫描完成”。文件或规则变化、修复代码后，核验受影响结论，未覆盖的必要范围保留缺口。

### 发现后处理与复验

以下处理适用于委派、scan 和宿主审查。用户明确只审不改时，返回经核实的发现与验证依据。

1. 核实问题：根据 OCR 建议定位材料，对照原请求、有效规则和当前代码读取上下文，复现或取得足够证据，排除误报。
2. 自行修复：问题确认且当前任务与授权覆盖时，以最小修改完成修复。遇到真实业务取舍、超出范围或权限缺口时，询问所需决定或授权，同时继续独立工作。
3. 复验并更新状态：按风险验证受影响用户路径或运行适当测试，再复审受影响文件。证据支持修复时标为已解决；未解决或无法复现时，保留具体状态和依据。后续 Git 提交、发送或发布按当前授权执行。

委派用法依据：上游 [v1.12.12 委派说明](https://github.com/alibaba/open-code-review/blob/182898cf522da3d04157b422752d028417974e19/pages/src/content/docs/zh/integrations/delegate.md)与[规则说明](https://github.com/alibaba/open-code-review/blob/182898cf522da3d04157b422752d028417974e19/pages/src/content/docs/zh/review-rules.md)；全文件模式依据[官方 README](https://github.com/alibaba/open-code-review#what-is-open-code-review)与当前 `ocr scan --help`。升级后核对当前 CLI 帮助、规则、输出及受影响行为。
