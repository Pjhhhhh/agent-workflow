## 全局规则的五类实际过程检查

全局规则检查使用正常配置下的原生 Codex 新会话与明确 ID 续接，写入范围限定在受控夹具。普通问答位于维护项目外，原生输入包含全局规则，未加载本项目 AGENTS；文件任务同时继承项目规则，结果按该受控条件归因。加载情况与实际行为分别记录。

| 过程 | 输入与实际操作 | 检查结果所需证据 |
| --- | --- | --- |
| 普通问答 | 项目外 read-only 会话回答简单自然问题 | 全局加载片段、实际回答及工具事件，检查直接表达和额外动作 |
| 只读审查 | 读取有明确输入和约定的受控代码，核对缺陷 | 真实正文、具体触发路径、原生工具日志及夹具未改动 |
| 代码与文档修改 | 获得指定文件修改授权，使用夹具已有检查入口 | 实际差异、真实检查输出，核对完整修改、验证及无关文件生成 |
| 用户纠正后继续 | 更新夹具内容并给出有效纠正 | 最新内容保留、受影响项修改及原任务连续性 |
| 途中问题与恢复 | 在原任务过程中提问，再用明确会话 ID 续接 | 回答、中间状态、原生 resume 续接事件及后续完成；强制压缩恢复需另行检验 |

五类过程均已实际观察，动作与文件结果达到当时样本要求。样本核对结果见[验证摘要](验证摘要.md#2026-11-05职责分流与技能接入核对)。

方法参考包括 Lance Martin 于 2026-09-28 发布的 [Automating eval design and hillclimbing with Claude](https://claude.dev/blog/automating-eval-design-and-hillclimbing/)，以及固定版本的[官方 build-eval 指南](https://github.com/anthropics/skills/blob/8a1541c4a3ffa5a20a5a91de0dcf3f0bab1d1ef4/skills/claude-api/shared/evals/build-eval.md)和 [hillclimb 指南](https://github.com/anthropics/skills/blob/8a1541c4a3ffa5a20a5a91de0dcf3f0bab1d1ef4/skills/claude-api/shared/evals/eval-hillclimb.md)。采用其中的真实场景、评审校准、固定条件、单项改动和防过拟合方法。

## 先固定三个本项目案例

| 案例 | 场景与任务 | 必要结果 | 如何观察 |
|---|---|---|---|
| T01 文档修改 | 修正文档中的当前计划约定 | 相关文件中新计划约定一致；写清旧档案与 .codex 实验状态的归属；修改限定为计划路径相关说明和忽略规则 | 对照冻结前后文件，按 UTF-8 重新读取，检查本地链接及修改范围 |
| T02 历史代码缺陷回放 | 本项目曾出现原要求、别名、符号链接与硬链接被当作完成证据的缺陷；使用修复前的真实源码快照 | 正常证据仍通过；拒绝原要求及同一文件身份冒用；保留该快照的 CLI 和权限边界 | 实际运行本地 score，保存输入、退出码、理由和前后差异；核对直接路径、等价路径及同一文件身份 |
| T03 资料研究 | 核查指定文章的参考情况，并设计固定真实任务的检验方式 | 来源支持结论；分别判断起始材料是否记录该参考、全部历史是否读过；分别标明资料取得情况及设计、实测状态 | 独立阅读请求、来源正文和回答，逐项核对主张，以依据和实际结果评分 |

上表公开案例设计，原始请求、派生任务说明和冻结工件保存在本地。T02 使用冻结的旧协议源码；历史 CLI 控制检查起始缺陷是否可复现，候选修复和模型试次按各自实际结果验收。精确命令与结果保存在本地案例记录。

每例固定原始请求或明确标注的派生任务、起始工件、必要验收、允许操作、可观察结果和恢复条件。复制起始状态后，在独立试次目录执行；目标程序或文件的位置可按试次重定位，其他条件保持一致。

## 从 T02 派生审查案例

以下审查案例从 T02 派生，沿用现有冻结、校准和 A/B 载体，保留原先 12 个代理试次的设计。目前已完成来源核对、案例定义和规则语义走查材料，独立候选版本尚未生成。

历史来源为本地 `.plan/真实任务检验/cases/T02-原请求冒用/` 的 `prompt.md`，以及冻结旧源码中 `evaluate()` 内的 `evidence()`；来源与 SHA256 见同一计划的 `cases.json`。当前实现定位到[评分器](../skills/work-eval/scripts/work_eval.py)的 `non_request_file()` 与 `evidence()`。正式执行前，按现有流程冻结所用版本、派生差异、请求和预期。

| 派生输入与可定位来源 | 预期 finding | 不应报项与修复后影响 |
| --- | --- | --- |
| R01 坏样例：T02 冻结旧源码的 `evidence()` 只要求已声明证据存在；沿原任务构造“仅以原请求作为必要项完成证据”的有效输入 | 原请求用于说明要求，完成情况须由结果证据证明；核对直接路径、等价路径、符号链接与硬链接的同一文件身份冒用 | 正常独立结果证据仍应通过。修复须拒绝冒用并给出理由、下一动作；修改限定在身份判断，保留旧快照 CLI、输入和退出码约定 |
| R02 未完成修复：在 R01 的原位置派生仅以 `p != request_artifact` 排除直接路径的候选，其他逻辑不变 | 直接路径可能已被拒绝，等价路径、符号链接与硬链接仍指向同一请求，身份判断缺陷尚未解决 | 按实际结果记录直接路径是否被拒绝，同一根因的不同别名合并记录。补足身份核对后，重新验证冒用与正常证据；读取错误仍按旧协议处理 |
| R03 安全反例：当前 `non_request_file()` 用 `samefile` 排除请求身份，缺失文件或 `OSError` 返回 False；`evidence()` 要求必要项有非请求证据且全部引用存在 | 核对完整调用和保护分支，确认同一身份冒用已被阻止后，记录反证；缺少额外字符串比较或手工路径归一化本身不构成缺陷 | 根据实际身份处理判断安全性，保留已有保护有效的实现。若实际输入绕过保护，附上触发证据并验证受影响范围 |

身份冒用及普通 bug 均按原 CLI 约定记录，包括正常证据被错误拒绝、缺失证据被错误放行，以及读取错误导致非约定退出。逐项记录核实后的有效发现、误报、已解决后的重复发现、复审轮数、人工处置和范围变化。同一份未修改代码在多轮审查中零散出现问题时，复查首轮覆盖；修复引入的新回归与已解决后重复报告的问题分别统计，必要修复完成后结束。

## 实验分五步

1. **保存起始案例。** 保留来源、初始文件及必要差异，检查目标是否可解、验收是否已写入任务；输入覆盖常规可完成的情况、真实困难和应保留未知的情况。
2. **校准评审。** 使用已知正确、空输出、只声称成功但实际没做三类样本，检查判断是否合理；对同一输出重复评审，核对不一致原因。复杂语义由独立模型或人工阅读原请求与真实工件，代码检查可确定部分。模型评审结果与人工样本校准后，再用于比较。
3. **固定对照。** A 为当前稳定规则，B 只改变一个待测因素，可删减、改写或移动规则；必要结果、允许操作，以及模型、推理设置、工具、权限、输入、环境、预算和用户反馈策略保持一致。每个试次从相同起始工件创建新环境。
4. **运行并保存证据。** 每个试次保存完整可取得的轨迹、原始输出、最终工件、差异、验收逐项判断、退出状态、耗时及可取得的用量。工具或环境故障单独标记，无法取得的费用或用量标明未知。
5. **保留有证据的改动。** 先核对必要要求的完整通过情况和具体错误，再比较耗时及成本；可靠证据支持改善时，才保留候选改动。评审或环境有缺陷时，先修复实验；更换评审版本后，对基线和候选全部重新评审。

代理任务以最终工件和实际状态判定完成，过程轨迹用于检查早停、越权及判断依据。资料研究允许如实回答资料不足；文档需要填写真实业务字段时，缺少数据的依赖项仍为未完成。两种结果按原任务的验收要求区分。来源为 [Anthropic 代理评测方法](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。

## 首轮规模与记录

首轮设计为 3 例×2 个规则版本×2 次重复＝12 个代理试次，用于检查环境、评审和改动方向。每个代理试次可能多轮调用工具和模型，校准、重新评审及重试所需调用分别计入记录。正式规模根据观察到的波动和希望识别的最小改善决定。

主结果按试次记录：必要项通过／失败／未验证、无依据事实、范围外操作、可继续却结束、人工纠正。必要项全部通过且没有实质越权时，才计为完整完成；明确允许的未知按原任务要求判断是否为正确结果。

首轮三例用于小规模试跑。扩大任务集后，优化者只读训练失败；逐轮选择版本时使用验证集，最后用未参与选择的保留集检验一次。这是本项目为扩大任务集提出的安排；官方详细指南给出较大集合的可选三分设计，博客主要描述 train／test 两分。反复查看并用于选择版本的“test”按验证集处理。

评测结果不符合预期时，核对任务、评审和基础设施，依据真实失败修复实验。

## 执行前须满足的条件

执行前，将模型、推理设置、评审方式和实验预算写入运行记录。实验运行器将超时记为未完成，完成判定继续采用原任务的必要结果；真实业务操作按原任务授权执行。

由运行环境将每个候选进程的访问范围限定为该试次允许的输入、工具和当前产物，隔离评审答案、其他试次、旧成功交付、评审代码、优化报告及历史记忆。执行前实际预检：读取允许文件应成功，读取评审及其他试次文件应被拒绝，结果符合要求后再开始试次。

本实验在项目根 `.plan/` 记录计划、案例和冻结清单，在启动目录 `.codex/` 保存运行日志和状态。需要独立保存运行记录或显式选择记录检查 CLI 时，按[任务跟踪约定](agents/issue-tracker.md)使用 `.codex/verification/<task_id>/<唯一run_id>/`；已有计划、必要日志和交付文件足够时沿用。冻结案例保留当时输入；新的约定用于新试次。原任务输入、冻结文件及私有执行记录在本地保留，公开可运行的协议演示见[示例说明](../examples/README.md)。
