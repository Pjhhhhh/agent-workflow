# 固定真实任务检验

当前状态：真实任务案例处于准备阶段，尚未运行模型对照或评测链的重复判题校准。具体冻结清单、输入数量和准备进度保存在本地计划。当前CLI回放项数及版本见[验证摘要](验证摘要.md)，回放只作为协议回归。模型对照应检查代理实际完成的结果、无依据结论、范围外操作和可继续却早停的情况。

方法参考包括 Lance Martin 于 2026-09-28 发布的 [Automating eval design and hillclimbing with Claude](https://claude.dev/blog/automating-eval-design-and-hillclimbing/)。采用其真实场景、评审校准、固定条件、单项改动与防过拟合原则；同时核对 [官方build-eval指南](https://github.com/anthropics/skills/blob/8a1541c4a3ffa5a20a5a91de0dcf3f0bab1d1ef4/skills/claude-api/shared/evals/build-eval.md)及 [hillclimb指南](https://github.com/anthropics/skills/blob/8a1541c4a3ffa5a20a5a91de0dcf3f0bab1d1ef4/skills/claude-api/shared/evals/eval-hillclimb.md)。本项目借用方法，没有安装或运行 claude-api 命令。

## 先固定三个本项目案例

| 案例 | 场景与任务 | 必要结果 | 如何观察 |
|---|---|---|---|
| T01 文档修改 | 修正文档中的当前计划约定 | 相关文件中新计划约定一致；写清旧档案与 .codex 实验状态的归属；只改计划路径相关说明和忽略规则 | 对照冻结前后文件，读回UTF-8，检查本地链接及修改范围 |
| T02 历史代码缺陷回放 | 本项目确实出现过原要求／别名／软硬链接被当作完成证据；使用修复前的真实源码快照 | 正常证据仍通过；原要求及同文件身份冒用不能通过；保留该快照的CLI和权限边界 | 实际运行本地score，保存输入、退出码、理由和前后差异；只匹配字符串的修复不足以完成 |
| T03 资料研究 | 核查指定文章的参考情况，并设计固定真实任务的检验方式 | 来源支持结论；起始材料未记录该参考与全部历史是否读过分开判断；已取得／未取得资料及设计／实测分开 | 独立阅读请求、来源正文和回答，逐项核对主张，不以篇幅或赞同程度评分 |

上表公开案例设计；原始请求、派生任务说明和冻结工件保存在本地。T02 由已复现的缺陷转为历史回放任务。这些案例用于校准和小规模试跑，尚不能代表全部日常任务。Word 字段填写、复杂应用操作等案例需要真实输入和可重置环境，准备好后再加入。

每例固定原始请求或明确标注的派生任务、起始工件、必要验收、允许操作、可观察结果和恢复条件。复制起始状态后在独立试次目录执行，目标程序或文件的位置可按试次重定位；其他条件保持一致。答案、旧成功交付、评审代码和优化报告不放进候选可读输入。

## 实验分五步

1. **冻结案例。** 保存来源、初始文件和SHA256，检查目标可解、验收已写进任务；包含常规能完成的情况、真实困难和应保留未知的情况，不只挑当前模型失败过的输入。
2. **校准评审。** 先用已知正确、空输出、只声称成功但实际没做三类样本，检查是否得到合理判断；对同一输出重复评审，核对不一致原因。复杂语义由独立模型或人工看原请求与真实工件，代码只检查可确定部分。
3. **固定对照。** A为当前稳定规则，B只增加一项待测规则；保持同一模型、推理设置、工具、权限、输入、环境、预算和用户反馈策略。每次新环境，不能接着上次的成功文件继续跑。
4. **运行并留证。** 每个试次保存完整可取得轨迹、原始输出、最终工件、差异、验收逐项判断、退出状态、耗时及能取得的用量。工具或环境故障单独标记，不混成模型错误；缺失费用或用量写未知，不填0。
5. **只保留有证据的改动。** 先看必要要求的完整通过和具体错误，再比较耗时及成本。没有可靠改善就不叠加规则；评审或环境有缺陷时先修实验，换评审版本后对基线和候选全部重评。

对代理任务，最终工件和实际状态决定完成；一句“已修复”不能替代结果。过程轨迹帮助查早停、越权与判断依据。资料研究允许诚实回答资料不足；文档若必须填写真实业务字段，缺数据的依赖项仍为未完成。这两种结果按任务原先的验收区分。[Anthropic代理评测方法](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

## 首轮规模与记录

先用 3 例×2 个规则版本×2 次重复＝12 个代理试次检查环境、评审和改动方向。这不等于 12 次 API 调用：一个代理可能多轮调用工具和模型，校准、复评及重试还需另计。首轮不宣称总体提升或显著性；正式规模根据观察到的波动和希望识别的最小改善决定。

主结果按试次记录：必要项通过／失败／未验证、无依据事实、范围外操作、可继续却结束、人工纠正。必要项全部通过才计完整完成；任何实质越权不能由平均分抵消。明确允许的未知可以是正确结果，不为求确定性逼代理猜测。模型评审结果先与人工样本校准，再用于比较。

首轮只把结果当探针，不把三例硬拆成每组一例后报告泛化。扩大任务集后，优化者只读训练失败；逐轮选版本使用验证集，最后用未参与选择的保留集检验一次。该安排是本项目建议，与官方详细指南针对较大集合的可选三分设计一致；博客本身主要描述train／test两分。反复查看并据此选版本的“test”已承担验证作用，不能再称完全未参与选择。

原文还把更强模型／更高推理是否通常更好视为评测诊断线索；本项目不把它当必须成立的排名规则。任务、评审或基础设施错误先诊断，不能靠调整要求得到漂亮分数。

## 执行前须满足的条件

模型、推理设置、评审方式及实验预算先写入运行记录；当前均未选定，尚未启动 12 个试次。任务超时由实验运行器记录为未完成，不允许被测代理自己把观察窗口当完成理由。真实业务任务沿用原有完成和权限要求。

每个候选进程只能接触该试次允许的输入、工具及当前产物；评审答案、其他试次、旧交付和历史记忆应被运行环境实际隔离。SHA只能发现文件变化，不能证明代理读不到答案。使用同一机器上的不同子代理也不自动形成文件权限隔离。预检需要观察允许文件能读取、评审与其他试次文件不能读取，才可称隔离已验证。

本项目在项目根 `.plan/` 记录计划、案例与冻结清单，在启动目录 `.codex/` 保存运行日志和状态；正式验收每次使用独立 `<task_id>/<唯一run_id>` 目录，位置和恢复规则见 [任务跟踪约定](agents/issue-tracker.md)。冻结案例保留当时的输入，后来的约定变更不改写历史案例。原任务输入、冻结文件及私有执行记录不随仓库发布；上表说明案例设计，公开可运行的合成例子见[示例说明](../examples/README.md)，不能把合成例子当作这些真实任务的替代。正式运行前先完成实际环境与评审预检。

T02 的历史缺陷来自冻结的旧 v2 源码，不代表当前 v3 存在相同缺陷。历史 CLI 控制只用于确认起始缺陷可复现，不能作为候选修复或模型试次通过；精确命令与结果保存在本地案例记录。
