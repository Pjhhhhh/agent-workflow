# 工作流程

本项目整理任务从接收到交付的路径，检查漏项、无效等待、证据覆盖不足和过早结束。图用于按需解释流程；推荐流程与脚本已实现的功能分别标注。

全局通用规则已包含实际执行、必要核验和按复杂度独立评审。通用技能通过用户级入口提供 v3 记录与检查；Stop 仍仅供维护项目内明确授权的实验。其他项目无需图集或维护项目的根标记。当前加载证据与扩大范围的条件见 [全局使用范围](全局使用范围.md)。

## 一个任务的完整路径

1. 先按 [默认工作流技能](../skills/work-eval/SKILL.md) 分流，从原始请求和最新有效纠正提取目标、必要结果与授权；进入 v3 时保存必要原文记录。旧记忆与外部资料用于查证，不获得新指令权限；用户追加要求后核对契约，按需更新并重评。
2. 先解决影响目标、必要验收或授权的不确定性，再选择对应工具实际执行。可逆技术细节沿用已有约定；缺真实业务信息或新权限时只暂停依赖部分，其他独立工作继续。多步骤工作保留当前计划、尝试、证据和下一动作。
3. 用目标对象的实际终态验证，保存实际差异或工具日志。代码写完、命令成功或截图生成分别是阶段证据；每条必要结果须有足够观察，原要求本身不能证明完成。
4. 简单任务直接对照必要结果核验；复杂任务或关键证据冲突时，独立评审先读原始要求，再对照最终答复、契约、工件及实际操作。逐条核对关键主张的事实/推断/未知、来源是否支持结论、操作是否服务获授权目标，并找清单外遗漏。必要失败或缺证据时回到具体缺口；不能仅写 partial 就结案。
5. 必要项通过后交付。真实外部阻碍、用户停止或硬预算时记录未完成、具体原因与恢复条件；权限由已有授权决定，验收不给新权限。

分流和逐步操作以 [默认工作流技能](../skills/work-eval/SKILL.md) 为准；计划归属与跨目录恢复优先遵守目标项目约定；本维护项目见 [任务跟踪约定](agents/issue-tracker.md)。图 05 展示复杂任务的 v3 验收路径，普通任务按实际分支执行。

具体判断和 v3 的实现边界见 [防编造与范围核查](防编造与范围核查.md)。独立读取可以并行，共享文件修改、授权与依赖步骤顺序执行；任务之外的新想法记录为候选，业务选择和额外权限未确定时不纳入实施。

必要验收项可以在现有描述中写清实际入口、前置条件、复现方式和应观察的终态。复杂产品按需维护功能入口索引；本项目现有 CLI 见 [验收功能入口](../skills/work-eval/references/features.md)。普通任务无需额外生成完整规格或新 JSON 字段。

Matt Pocock及Lauren／Poteto的实际参考、已采用方法和未取得篇章见 [流程参考与取舍](流程参考与取舍.md)，不将文章中的效果描述当成本项目通过证据。

每次回修都要明确：哪些工件或实际状态证明结果，谁从缺口中选择下一动作，谁执行修改，修改后检查哪些受影响项。现有分工即可完成：独立评审核对结果，主代理选择并执行动作，脚本检查记录结构与版本；单个小项通过后继续原任务。这借用了 HumanLayer 的测量、选择动作与执行分工，没有新增自动调度器。[原始设计指南](https://github.com/humanlayer/skills/blob/ca7c8088db69e315a8b2deea43820270457f8f3c/plugins/design-control-loop/skills/design-control-loop/SKILL.md)

## 研究进入计划前，核对决定修改的依据

陌生代码链路、来源冲突或跨模块变更需要调查时，先在现有 `findings.md` 区分当前事实、推断、未知与拟议方案。方案进入计划前核对三个问题：原请求是否需要这项修改；关于当前链路的判断是否有直接来源；验证动作能否观察原问题的终态。来源写明文件或页面、正文位置及版本，不把调查建议直接变成验收要求。

这借用了 HumanLayer 将研究、计划与实现分别整理、提前审阅关键判断的方式。2025 年文章中的实践依赖人的审阅；本项目在既有授权内由执行者核对，适用规则要求独立评审时交给评审者，缺真实信息、业务选择或新权限才询问用户。这是本项目的适配，尚未验证它与原做法是否取得相同效果。简单任务可直接执行，不增加固定的研究审批阶段。[官方上下文工程文章](https://www.humanlayer.dev/blog/advanced-context-engineering)

阶段切换或压缩时，只把下一阶段需要的有效要求、关键依据、已验证和未完成项、失败位置与下一动作放进摘要，引用原文件供复读。长日志保留原件，摘要写错误位置、输入、关键报错和影响；工具输出截断或证据不足也要记录。压缩不能把推断改成事实，或把已知失败删成“基本完成”。恢复规则见 [防编造与范围核查](防编造与范围核查.md)。

## 四类任务共用流程，采用不同验证

| 任务 | 应观察的终态 | 常见遗漏 | 最小证据 |
| --- | --- | --- | --- |
| 代码 | 原失败输入走实际用户链路得到约定结果，必要既有行为保持 | 局部回归绿而原问题仍红；错误降级掩盖未完成 | 输入、真实结果、trace 或日志、复现命令 |
| 文档 | 固定原模板及允许变更，保存后重开或渲染，对照输出结构、格式、公式和字段 | 原件未改或输出显示正常，却擅自改了模板结构和格式 | 模板与输出对照、字段及相关版面核验，见[文档模板核验](防编造与范围核查.md#文档模板核验) |
| 电脑操作 | 指定程序采用目标配置，原问题在实际调用中消失 | 编辑了非生效副本，版本更新但调用仍失败 | 生效路径、原生诊断、前后状态 |
| 研究 | 原问题得到可追溯回答，事实、推断、旧信息和未知明确 | 引文存在但不支持结论；旧摘要升级成当前事实 | 主张对应正文、日期或版本、反证与未知 |

## 普通任务与 /goal

本项目内的普通实质任务默认使用相同的验收流程。技能负责提醒和组织工具，目标运行机制负责持续调度；两者不是同一组件。`/goal` 只在用户明确要求时使用，目标满足、硬预算或用户停止仍各有明确退出状态。命令可用性依宿主与版本，本项目不提供 `/goal` 命令实现。[官方长任务说明](https://learn.chatgpt.com/docs/long-running-work)

目标描述可写成“目标结果、必要验收、授权边界、证据、退出条件”。先用现有计划记录即可；没有真实重复需求时，不为这一段描述再造一个技能或框架。

## 图与子代理的用途

| 工具 | 本项目用途 | 使用时机 |
|---|---|---|
| Archify | 从确定的流程、状态和架构生成独立HTML图；沿用当前四张图的结构与浏览器验证 | 修改流程图源或需要解释新的技术链路时使用 |
| Graphify | 从源码和文档提取关系，查调用链、依赖和影响范围；维护者可在本地按需生成graphify-out | 需要理解代码关系或源码修改后更新AST时使用，返回当前源码／运行证据确认判断 |
| diagram-design | 绘制时间线、矩阵、甘特、鱼骨等更多图类，也能画流程图 | 图类、版式或导入素材需要时选用；已有Archify图无需重复生成一份 |

Archify与diagram-design的绘图能力有重叠，选满足当前交付的一种即可。Graphify提供关系线索；三者都不替代功能验收，也不决定是否自动执行任务。

流程图帮助理解依赖、返修路径和阻碍；代码知识图帮助查找文件关系和影响范围。本地生成的代码与文档关系图可用于导航，Graphify 的静态关系用于导航，重要判断仍需回到源码或运行证据。每项任务是否使用图，按实际需要决定。

独立评审可交给一个子代理，直接提供原始要求与实际对象。只读子代理返回结果，父代理原样保存正式评审 JSON 并汇总整体验收，子代理不为本次委派再建验收链。确定性合并、排序和哈希由代码处理。只有能清楚分配独立调查范围时才增加并行代理，不能把同一证据窗口复制多次当作多个独立观点。[官方 evaluator-optimizer 模式](https://www.anthropic.com/engineering/building-effective-agents)

## 学习路径

具体固定任务、校准评审、对照与保留集方法见 [真实任务检验](真实任务检验.md)。用户指定的 [Anthropic eval与hillclimbing文章](https://claude.dev/blog/automating-eval-design-and-hillclimbing/) 已在历史准备阶段加入参考；协议回归项数以对应运行 report 为准，不作为真实模型的完成率。

先用真实失败定位薄弱步骤，再修改一个有针对性的规则、工具或验证。与简单基线、未参与调参的保留任务比较完整成功、漏项、返工、人工催促及成本。没有对照数据时，只记录改进假设，不宣称可靠性提升多少。[吴恩达的错误分析方法](https://www.deeplearning.ai/the-batch/improve-agentic-performance-with-evals-and-error-analysis-part-2/)
